# Backend audit - chatsystem (NestJS)

Read-only static analysis of /home/mushigarou/AI_Lab/chatsystem (commit e62e910e). Nothing was run; every claim below was checked against the source. Items marked "suspected" were not confirmed. Secret values are not printed.

## 1. Architecture (as implemented)

Two live processes, one stub, three backing stores.

| Component | Port (env) | Role | State |
|---|---|---|---|
| `apps/chatsystem` | `CHAT_PORT ?? PORT ?? 3000` | Stateless REST under `/api/*` (Express). Owns all writes: users, guilds ("collectives"), channels ("rooms"), invites, messages, DMs, friends, voice join/leave, presence. Serves static `client/` (dir does not exist) | working |
| `apps/gateway` | `GATEWAY_PORT ?? PORT ?? 3001` | Raw `ws` WebSocket on `/gateway` + 2 HTTP routes (`POST /gateway/url`, `GET /gateway/stats`). Holds sockets, fans out Kafka events. Reads Postgres directly (SessionLoader) and Redis (presence) | working |
| `apps/voice-signaling` | `process.env.port ?? 3000` (lowercase) | Nest "Hello World" scaffold. Not in `start:dev` | stub |
| `libs/common,config,database,kafka,redis,scylla,snowflake` | - | Seven empty `@Injectable() class X {}` shells. Imported by nobody (no `@app/*` import anywhere under `apps/`) | dead |
| PostgreSQL 16 | 5432 | Source of truth (Prisma 7 + pg adapter). Tables: user, guild, channel, member, role, message, friendship, invite, direct_channel, direct_channel_member | used |
| Kafka (apache/kafka 3.8, single node KRaft) | 9092 | Topics `messages`, `presence`, `voice_state` | used |
| Redis 7 | 6380 effective (see B-23) | Only the gateway uses it: key `user:{id}:presence` (JSON, TTL 300s) | used |
| ScyllaDB | - | Not in compose, not in code (`cassandra-driver` in package.json, never imported) | absent |

Edges (for the diagram):
- Browser -> chatsystem: HTTP REST (JSON). Identity is a `userId` in query string or body. No token.
- Browser -> gateway: WebSocket. Op 2 IDENTIFY with `token` = the user id as a decimal string.
- chatsystem -> Postgres: Prisma (all CRUD).
- chatsystem -> Kafka: produce only (messages, presence, voice_state). Key `channel:{id}` / `user:{id}` / `guild:{id}`. No consumer in chatsystem.
- gateway -> Postgres: read-only at IDENTIFY (user, member -> guild -> channels, friendships).
- gateway -> Redis: SET/DEL/EXPIRE/MGET `user:{id}:presence`.
- gateway -> Kafka: creates the 3 topics (3 partitions) at boot; produces `presence`; consumes all 3 with a random group id per process (`gateway-<uuid>`) so every gateway instance sees every event.
- gateway -> browser: DISPATCH frames: READY, MESSAGE_CREATE, PRESENCE_UPDATE, TYPING_START, VOICE_STATE_UPDATE. Heartbeat 41.25 s, identify timeout 10 s, slow-consumer drop at 1 MB buffered, in-memory replay buffer of 100 frames per channel.
- voice-signaling: connected to nothing. `joinVoice` only flips `member.voiceChannelId` in Postgres, emits a Kafka `voice_state` event, and returns a placeholder SFU URL (`wss://sfu.local.example/stream`).

Topic produce/consume matrix:

| Topic | Producer | Consumer | Notes |
|---|---|---|---|
| messages | chatsystem (create, edit, delete) | gateway | edit/delete are dispatched as MESSAGE_CREATE (B-05) |
| presence | chatsystem (`PATCH users/:id/presence`), gateway (connect/disconnect/op 3) | gateway | Redis is updated only by the gateway path (B-12) |
| voice_state | chatsystem | gateway | no gateway-side producer |

No topic is orphaned, but nothing else ever reads them, so Kafka is used purely as a chatsystem -> gateway pipe.

Startup order: Postgres + Kafka + Redis up -> `prisma migrate deploy` -> `db:seed` -> gateway (creates topics) -> chatsystem (must start after Kafka is reachable; see B-07) -> front-end.

## 2. Message flow (as implemented)

Guild channel message, A -> B:
1. A: `POST /api/rooms/:channelId/messages` with body `{senderId, message}`. `senderId` is taken from the body, never authenticated (`app.controller.ts:119-127`, B-01).
2. `ChatService.createRoomMessage` (`chat.service.ts:304`): trims, rejects empty or over 4000 chars, resolves the id against `channel` then `direct_channel`, checks guild membership (or DM membership) for `senderId`.
3. `prisma.message.create` (serial `message_id`, not a snowflake). Row is committed.
4. `kafka.publish('messages', 'channel:<id>', payload)` is fire-and-forget (`void`, line 328). If the producer never connected or the send fails it logs a warning and returns false: the message is stored but never pushed (B-07, B-17).
5. HTTP 201 returns the shaped message to A. A's UI shows it from the HTTP response.
6. Gateway KafkaService `eachMessage` -> `EventsConsumer.onMessage` -> `registry.remember` (replay buffer) + `registry.toChannel(channelId)` -> every local session whose `channelUsers` index contains that channel gets `MESSAGE_CREATE`. This includes A's own sockets (no dedupe; the client must dedupe by id).
7. B receives it only if B's socket was IDENTIFYed after B joined that guild and the channel existed (channel set is frozen at IDENTIFY, B-03).

Where it breaks:
- **DM A -> B**: steps 1-5 work. At step 6 the DM channel is not in anyone's `channelUsers`, because `SessionLoader` loads only guild channels (`session-loader.service.ts:341-365`). DMs are never pushed in real time (B-02).
- **Edit/delete**: published with `type: MESSAGE_EDIT|MESSAGE_DELETE`, but `EventsConsumer.onMessage` ignores `type` and always emits `MESSAGE_CREATE` (B-05).
- **Auth**: at both HTTP and WS, identity is a self-asserted user id (B-01).
- **Late joiner**: guild joined or channel created after connect gets nothing until reconnect (B-03).
